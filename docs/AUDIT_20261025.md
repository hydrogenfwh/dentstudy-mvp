## 本轮问题与修改代码

### 一 较早的未读通知无法通过界面消除

原先仅依据最近一页通知计算通知标签的未读数。一页最多 50 条，但首页共享红点使用后端的全部未读总数。例如共有 87 条未读，读完当前可见通知后，较早通知仍然未读，而页面没有明确的处理入口。

修改位置：[social_inbox_page.dart](/Users/hydrogen/Documents/ChatGPT/dentstudy/mobile/lib/features/social/social_inbox_page.dart:165)。现在保留后端精确总数，自动已读仅提交当前可见通知 ID；通知标签显示明确的“全部已读”按钮，只有用户主动点击才确认较早通知。按钮执行中禁用重复操作，失败不会伪装成已读。旧后端若还返回私信唤醒通知，仍避免与聊天重复计数。

```dart
final visibleUnread = items.where((item) => item['readAt'] == null).length;
var nextUnread = legacy
    ? visibleUnread
    : (result['unreadCount'] as num?)?.toInt() ?? visibleUnread;
// 可见通知按 ids 确认；只有明确点击“全部已读”时才省略 ids。
final result = await store.markNotificationsRead();
```

回归在 360、390、768、1440 宽度分别验证：初始 87，查看一条后仍为 86，不自动读取其余通知；点击全部已读后共享红点总数变为 0。

### 二 电脑端切换聊天对象会串用草稿和异步发送状态

桌面双栏复用同一个 `_ChatThread` 状态，切换对象只更新消息列表，没有隔离输入框及尚未结束的发送请求。由此可能将甲的未发送文字显示在乙的输入框，或让甲的迟到响应影响乙的界面。

修改位置：[social_inbox_page.dart](/Users/hydrogen/Documents/ChatGPT/dentstudy/mobile/lib/features/social/social_inbox_page.dart:490)。以好友 ID 为聊天子组件设置 Key，按对象隔离整个状态；发送成功后先确认组件仍存在，再访问控制器。

```dart
_ChatThread(
  key: ValueKey(_profileId(friend)),
  friend: friend,
  // 其余回调保持原有行为。
)
// await 之后，必须先判断 mounted，再访问 composer。
if (!mounted) return;
```

回归覆盖：甲草稿不出现在乙输入框；发给甲后立刻切乙，甲的延迟响应不会出现在乙的消息列表，不清空乙的新草稿，不访问已释放的控制器。切换时不保存离开的未发送草稿；本次没有新增跨会话草稿持久化功能。已提交到服务器的甲消息不会因切换对象而取消或改发给乙。

### 三 发送完成或失败会清空正在新写的下一条草稿

原先发送响应回来时无条件清空输入框。如果等待期间继续输入下一条消息，新文字也会被清掉。

修改位置：[social_inbox_page.dart](/Users/hydrogen/Documents/ChatGPT/dentstudy/mobile/lib/features/social/social_inbox_page.dart:763)。记录提交时的原始草稿，只在输入框仍等于该草稿时清空；成功和失败分支都执行同样判断。

```dart
final draft = composer.text;
// 发送请求完成后：
if (!mounted) return;
if (composer.text == draft) composer.clear();
```

两个专门回归分别让接口成功、403 失败，均确认“下一条草稿”仍在。失败消息仍保留原来的“未送达”标记。
